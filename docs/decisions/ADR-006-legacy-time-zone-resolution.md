# ADR-006: Legacy Time Zone Resolution for legend-engine

**Status:** Accepted. Implemented in `legend-pure-m4`, `legend-pure-runtime-java-engine-shared`, both
engines, and the relational store runtimes.
**Date:** 2026-10-06
**Deciders:** Legend Pure core team

## Context

Pure resolves a time zone name strictly, with `ZoneId.of` against `ZoneId.SHORT_IDS`, which reads
regions, the three letter abbreviations, and offsets in every form, and rejects a name that stands
for no zone. A date pattern's zone has been resolved that way since 5.97.0, and every name since
5.99.0, when `TimeZones`, in `org.finos.legend.pure.m4.tools.time`, became the one place names are
resolved and the relational natives moved to it. Before that, names were resolved through
`TimeZone.getTimeZone(String)`, which reads an offset only with a `GMT` prefix and answers every name
it does not know with GMT. A bare `+0530`, an offset prefixed `UTC`, a misspelled region, and a
region still carrying the quotes an older connection grammar parser stored with it all read as GMT,
and nothing said so. 5.96.0's `DateFormat` resolved the zone of a date pattern that way, and so did
legend-engine where it read the dates in a result set and where it wrote a date with a format string;
its plan date parameters and its H2 extensions used `ZoneId.of`.

legend-engine is returning its own date and time zone handling to what it was before it adopted
strict resolution. It cannot do so without Pure, because legend-engine runs Pure: every execution
plan is generated by Pure code, and that code writes SQL date literals with a format string naming
the connection's zone, as `'%t{[' + $dbTimeZone + ']yyyy-MM-dd HH:mm:ss}'`. Under strict resolution
a model whose connection names its zone as `'US/Arizona'`, quotes and all, fails plan generation as
soon as a date is written; under the old behavior it generated a plan whose literals were written in
GMT. Going back on strict resolution in Pure would undo it for everyone else too.

## Decisions

### 1. Two resolutions, named

`TimeZoneResolution`, beside `TimeZones`, has two constants, and both resolve through `TimeZones`.
`STRICT` uses its `parse`, `parseTimeZone`, and `newCalendar`, which resolve through `ZoneId.of`
against `ZoneId.SHORT_IDS` and reject a name that stands for no zone. `LEGACY` uses its
`parseLegacy`, `parseTimeZoneLegacy`, and `newCalendarLegacy`, which resolve through
`TimeZone.getTimeZone(String)`, with all its flaws, and convert with `TimeZone.toZoneId()` wherever a
`ZoneId` is wanted. java.time cannot represent a `GMT` offset of more than 18 hours, which java.util
accepts, so such a name resolves to a `TimeZone` but fails to convert to a `ZoneId`, just as it
failed in 5.96.0's `DateFormat`. Either way a name can be parsed to a `ZoneId`, to a `TimeZone`, or
into a `Calendar`, and both reject a null name, which is a caller's mistake rather than a name.

The legacy methods sit beside the strict ones they differ from. They and `LEGACY` are deprecated, so
that any use of them outside the one legend-engine needs is flagged where it is written.

### 2. Pure means strict

Every existing API that resolves a name still resolves it strictly. The legacy resolution is reached
only by asking for it: `DateFormat.format` and `DateFormatPattern.parse` gain overloads taking a
`TimeZoneResolution`, and `DateFormatPattern.Builder` gains `timeZoneResolution`. `PureDate` does
not change. The `format` natives call `DateFormat.format` directly rather than through the date, so
the language a format string is written in is the one it is rendered in, whatever class implements
the date.

### 3. A runtime option asks for it

The runtime option named `LegacyTimeZoneResolution` asks for the legacy resolution.
`TimeZoneResolutionOption`, in `legend-pure-runtime-java-engine-shared`, holds the name, answers
which resolution a set of `RuntimeOptions` asks for, and sets the resolution a
`MutableRuntimeOptions` asks for; it is the one place the natives ask, and the place a caller sets
it.
`RuntimeOptions` itself does not change: it is the general interface every option goes through, and
this one exists to manage a transition. legend-engine sets the option on the execution support its
`PureModel` builds; nothing else should. The option is read each time a name is resolved, so a
`MutableRuntimeOptions` toggled at run time takes effect at once, and like any option it can be set
for every runtime on the default options with the system property
`pure.options.LegacyTimeZoneResolution=true`.

### 4. Everything a running Pure resolves honors it

`format` in both engines, and `executeInDb` and the `fetchDb...MetaData` natives in both engines,
resolve their names as the option says. The relational natives read the same connection zones the
SQL literal writers splice into format strings, and one option meaning two different things in two
places would be worse than either.

### 5. Only the resolution changes

What a zone name resolves to is the whole of the difference. What the format language means, from
`z` writing the name as given to `Z` and `X` requiring an hour, how a DATE or TIMESTAMP column is
read, and every other date behavior are the same in either mode. In particular no calendar
arithmetic returns: a zone the legacy way resolves is shifted with java.time, exactly as 5.96.0's
`DateFormat` shifted it.

### 6. Compile-time checking stays strict

A literal format string is checked when Pure code is compiled, and it is checked strictly whatever
the option says. Options belong to a runtime that is running, and a literal that only the legacy
resolution accepts is a mistake in Pure source.

## Consequences

- A zone name means one of two things, depending on who runs the Pure. The same model can generate a
  plan under legend-engine and fail in the Pure IDE, or have its dates shifted in one and not the
  other. That is the cost, and it is why the legacy resolution is confined to an option nothing sets
  by accident.
- Any runtime legend-engine builds some other way than through `PureModel`, such as for its Pure test
  suites, runs strictly, while its tests through `PureModel` run the legacy way. Fixtures shared
  between the two should avoid the names the two read differently: bare offsets, offsets prefixed
  `UTC`, quoted names, and names that stand for no zone.
- A `DateFormatPattern` holds the zone a name resolved to as well as the name, and two patterns are
  equal only if both agree: `[+0530]HH` parsed strictly is not the pattern parsed the legacy way.
- The `format` natives no longer ask the date to format itself. The one implementation that answered
  differently, `LatestDate`, throws from every getter the same error its own formatting threw, so a
  format string that reads anything from `%latest` fails as it did; one that reads nothing from it,
  such as `%t{"x"}`, now writes its literal text.
- The legacy resolution is retained temporarily. Removing it is removing `LEGACY`, the legacy
  methods of `TimeZones`, `TimeZoneResolutionOption`, and the overloads that take a resolution;
  nothing else depends on them.

## Rejected

- **Going back to `TimeZone.getTimeZone` in Pure.** It would bring back the silent GMT everywhere Pure
  resolves a name, to solve a problem that belongs to one caller.
- **Strict first, then legacy for a name strict resolution rejects.** It would read `+0530` as five
  and a half hours ahead of UTC where legend-engine read GMT, so it would not restore the behavior it
  exists to restore.
- **A system property alone.** A system property holds for a whole JVM, and legend-engine hosts Pure
  executions besides its own plan generation that should stay strict. That the option can be set as
  one is a by-product of `RuntimeOptions.defaultOptions()`, not the mechanism.
- **A method on `RuntimeOptions`.** `RuntimeOptions` is the interface every option goes through, and
  a method there answering one transitional question would outlive the reason for it in the one
  place that is hardest to change.
- **Switching only `format`.** The relational natives resolve the same names, so an option switching
  one and not the other would be two options under one name.
