# ADR-007: Write-If-Modified for Generated Maven Plugin Output

**Status:** Accepted
**Date:** 2026-10-14
**Deciders:** Legend Pure core team

## Context

The Maven plugin pipeline in `legend-pure-maven/*` (`legend-pure-maven-generation-platform-java`,
`legend-pure-maven-compiler`, `legend-pure-maven-generation-par`, `legend-pure-maven-generation-java`,
`legend-pure-maven-generation-pct`) regenerates its output on effectively every build: M3
`CoreInstance` accessors, compiled-mode Java sources (one file per Pure class/function), `.par`
repository archives, the compiler's binary element files, and PCT reports. Several of the
generator/serializer classes behind these plugins wrote their output with a plain
`Files.write(path, bytes)` or `Files.newOutputStream(path)`, which unconditionally truncates and
rewrites the target file, every time, even when the newly generated bytes are identical to what is
already on disk. The practical effect is that files are reported as modified on every build
regardless of whether anything actually changed, which defeats Maven's own up-to-date checks, an
IDE's incremental compiler, and any downstream tooling (including `legend-engine`'s build) that
relies on file modification time to decide whether to do work.

One write path had already hit this problem concretely: `FileSerializer`
(`legend-pure-m3-core`, used by `legend-pure-maven-compiler` to write `.pelt` binary element files)
was fixed in #1235 ("fix: atomic write-if-modified in FileSerializer to prevent .pelt corruption")
with a private `writeIfModified` helper — write to a sibling `.tmp` file, compare byte-for-byte
against the existing target, and only atomically replace it if the content differs. That fix was
local to one class and was not applied to the other write paths, one of its own methods
(`serializeModuleBackReferenceIndex`) was missed, and the Maven-plugin-level symptom (unnecessary
file modifications) remained everywhere else.

## Decision

Extract the write-if-modified logic into a single shared utility, `FileWriteTools` in
`org.finos.legend.pure.m4.tools` (`legend-pure-m4`), and use it at every site that writes generated
or serialized output to disk:

- `FileSerializer` (`legend-pure-m3-core`) — all `serialize*(Path, ...)` methods, including
  `serializeModuleBackReferenceIndex`, which previously bypassed the write-if-modified helper.
- `JavaSourceCodeGenerator.javaClassesToDisk` (`legend-pure-runtime-java-engine-compiled`) — one
  `.java` file per generated Pure class/function; the highest file count of any write site.
- `M3ToJavaGenerator` (`legend-pure-m3-bootstrap-generator`) and `M3LazyCoreInstanceGenerator`
  (`legend-pure-m3-core`) — M3 `CoreInstance` accessor generation.
- `PureJarSerializer.writePureRepositoryJars` (`legend-pure-m3-core`) — the `.par` repository
  archive, via the stream-based overload.
- `Shared.writeStringToTarget` (`legend-pure-m3-core`, `pct.shared.generation`) — PCT reports.

`FileWriteTools.writeIfModified` is placed in `legend-pure-m4` because `m4` is the common dependency
leaf for every affected module (`m4` ← `legend-pure-m3-bootstrap-generator` ←
`legend-pure-m3-core` ← `legend-pure-runtime-java-engine-compiled`), so the helper is reachable
everywhere it's needed without introducing a new cross-module dependency. It exposes:

```java
boolean writeIfModified(Path targetPath, byte[] content) throws IOException;
boolean writeIfModified(Path targetPath, IOConsumer<OutputStream> writer) throws IOException;
```

The stream-based overload writes to `<target>.tmp`, compares it against the existing target
(size, then byte-for-byte), deletes the tmp file and leaves the target untouched if they match, and
otherwise atomically `Files.move`s the tmp file over the target
(`ATOMIC_MOVE` + `REPLACE_EXISTING`, falling back to a non-atomic replace if the filesystem doesn't
support atomic moves). If the writer callback throws, the exception propagates immediately and the
target is left completely untouched.

A static method taking a writer callback was chosen over an `OutputStream` subclass that would
compare-and-promote in `close()`. The callback form ties the promote decision to the writer callback
returning normally: if it throws, the method returns without ever touching the target, leaving only
an orphaned `.tmp` file. An `OutputStream`-based design is harder to make safe here, because
try-with-resources calls `close()` even when the try-block throws — a naive implementation would
promote a half-written temporary file over the real target on a failed write, which is worse than
the problem being fixed. Making that safe needs extra abort/commit state tracking for no benefit,
since every call site adapts to the callback form in one line.

### Related fix: deterministic `.par` archives

While adding a regression test for `PureJarSerializer`, archives generated from identical input were
found to differ byte-for-byte between runs, because `PureRepositoryJarBuilder` created every
`JarEntry` (the manifest, the two indexes, and each per-source entry) without an explicit timestamp,
so each inherited the wall-clock time at the moment it was written. `write-if-modified` only helps
when two runs over identical input produce identical bytes, so this was fixed in the same change:
every entry written by `PureRepositoryJarBuilder` now gets a fixed, explicit timestamp
(`JarEntry.setTime(0L)`), and the manifest entry — previously written internally by the
`JarOutputStream(OutputStream, Manifest)` convenience constructor with no way to override its
timestamp — is now written explicitly so the same fixed time can be applied to it too.

## Consequences

**Positive:**

- Re-running any of the five plugins with unchanged input no longer touches files whose content
  didn't change, so Maven's up-to-date checks, IDE incremental compilation, and downstream consumers
  (notably `legend-engine`'s build) stop seeing spurious modifications.
- The fix is concentrated in one well-tested utility (`TestFileWriteTools`) rather than duplicated or
  partially applied per call site.
- `.par` archives are now reproducible: the same input always produces the same archive bytes, which
  was a prerequisite for write-if-modified to have any effect there and is independently useful for
  build caching/signing.

**Negative:**

- Every write now does an extra read-back-and-compare pass (bounded by `COMPARE_BUFFER_SIZE`) and a
  temporary file, which is a small constant overhead per file even when content does change. This is
  outweighed by the avoided downstream rebuilds.
- The compare-then-move is not atomic as a whole (documented on `FileWriteTools.writeIfModified`); a
  concurrent writer could race with the comparison. This was already an accepted tradeoff in the
  original `#1235` fix and holds here for the same reason: writers are deterministic for a given
  logical input, so a race produces the same bytes being written twice, not corruption.
- `.par` entry timestamps are now fixed at 1970-01-01 (clamped to 1980-01-01 by the DOS time format)
  rather than reflecting generation time; nothing in the codebase was found to depend on `.par` entry
  timestamps being meaningful.

## Rejected

- **`OutputStream` subclass that commits in `close()`.** See above — unsafe under
  try-with-resources semantics without additional abort/commit tracking, for no real benefit over the
  callback form.
- **Leaving `.par` generation out of scope.** Applying `writeIfModified` to
  `PureJarSerializer` without also fixing archive determinism would have added overhead (temp file +
  compare) without ever skipping a replace, since the bytes would differ on every run anyway.
